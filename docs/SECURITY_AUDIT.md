# 安全审计

审计范围：公开仓库的 PHP 运行代码、测试、文档和发布脚本。审计结论基于静态检查与本地合同测试，不替代真实服务商沙箱和目标 V10 环境验证。

## 结论

未发现已知的严重或高危问题。发布前检查未发现真实凭据、个人路径、服务器地址、私有域名或私有更新系统内容；文档和默认配置仅使用 `example.com` 保留域名。

## 已验证控制

- 收银台提交和回调站点都强制 HTTPS。
- 支付请求使用 POST hidden input，不把签名字段改为 GET 查询串。
- 表单只有一个 redirect 能力标记，不包含自动提交 JavaScript。
- 商品名称去除标签和控制字符，输出 HTML 时对属性值转义。
- 异步通知在核心入账前验证签名、商户、成功状态、金额、支付通道、支付意图与订单归属。
- 同步返回不调用核心入账。
- 金额以十进制字符串规范化和比较，不使用浮点完成最终财务判断。
- 订单和平台流水使用数据库唯一索引及 MySQL 命名锁抑制并发重复入账。
- 错误响应和审计日志不记录商户密钥或完整通知载荷。
- 插件不声明自动退款能力。
- `install()` 与 `upgrade()` 使用同一幂等迁移；`uninstall()` 保留财务核对表。

## 已知剩余风险

### 历史签名算法

易支付 V1 使用 MD5 加商户密钥的兼容签名格式，不是现代标准 MAC。只能通过 HTTPS、强随机密钥、服务商访问控制、后台权限控制和密钥轮换降低风险。插件不能在不破坏协议兼容性的前提下替换该算法。

### 服务商实现差异

“易支付 V1”存在多种实现。不同服务商可能改变字段、编码、通道值或回调方式。接入前必须在服务商沙箱验证，不能仅凭接口名称假定完全兼容。

### 核心事务边界

插件在调用 V10 核心 `order_pay_handle()` 前后执行自己的核对和意图更新，但无法把核心内部交易与插件表更新合并成一个公开的跨层事务。重复通知路径会复核核心交易以收敛状态，仍需监控核心返回异常和数据库故障。

### 目标版本验证

代码按本地 V10 10.4.6 源码合同和 PHP 7.3 语法约束整理。部署到其他 V10 小版本前，必须在同版本副本中执行安装、支付、回调、重复回调、升级和回滚验证。

## 发布者检查

每次发布前运行：

```bash
sh scripts/check.sh
sh scripts/build-release.sh
```

再人工确认压缩包文件清单、SHA-256、Git diff 和生产配置不在仓库中。安全问题请按仓库根目录的 `SECURITY.md` 私下报告。
